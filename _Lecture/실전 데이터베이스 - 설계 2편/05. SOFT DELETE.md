# SOFT DELETE

## 1. SOFT DELETE가 필요한 이유

 - __SOFT DELETE가 필요한 이유__
    - 복구가 어렵다.
        - DELETE로 삭제한 데이터는 영구적으로 사라진다.
        - 데이터베이스에서 물리적으로 제거되었기 떄문에 일반적인 방법으로는 복구할 수 없다.
    - 연관된 데이터가 함께 사라진다.
    - 법적, 비즈니스적 요구사항
        - 전자상거래법에 따르면 거래 기록은 5년간 보관해야 한다. 세금 관련 자료도 일정 기간 보관 의무가 있다. 회원이 탈퇴했다고 관련 거래 기록까지 삭제하면 법적 문제가 생길 수 있다.
        - 비즈니스 분석이 필요할 수 있다. 탈퇴한 회원도 포함해서 매출 분석, 고객 행동 분석을 해야할 떄가 있다. 데이터가 삭제되면 정확한 분석이 불가능하다.
    - 삭제 시점을 알 수 없다.
 - __HARD DELETE의 문제점__
    - 복구 불가: 삭제된 데이터는 일반적인 방법으로 복구할 수 없다.
    - 연관 데이터 처리: 외래 키로 연결된 데이터 처리가 복잡하다.
    - 법적 요구사항: 일정 기간 데이터 보관 의무를 충족하기 어렵다.
    - 분석 불가: 삭제된 데이터는 통계나 분석에 포함할 수 없다.
    - 감사 추적 불가: 언제, 누가 삭제했는지 추적하기 어렵다.
    - 삭제 시점 불명: 데이터가 언제 삭제되었는지 알 수 없다.

## 2. SOFE DELETE - 컬럼 방식

### 2-1. is_deleted 컬럼 방식

가장 기본적인 방식인 is_deleted 컬럼을 사용할 수 있다.

 - `한계`
    - 삭제 시점을 알 수 없다.
    - 일정 기간 후 영구 삭제 정책을 적용하기 어렵다.
    - 복구 이력을 관리할 수 없다.
```sql
CREATE TABLE member (
    member_id BIGINT AUTO_INCREMENT PRIMARY KEY,
    username VARCHAR(50) NOT NULL,
    email VARCHAR(100) NOT NULL,
    phone VARCHAR(20),
    is_deleted BOOLEAN DEFAULT FALSE,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP
);
```
<br/>

### 2-2. deleted_at 컬럼 방식

is_deleted는 삭제되었는가라는 상태만 저장하지만, deleted_at은 언제 삭제되었는가라는 시점을 저장한다. 이 시점 정보만으로 삭제 여부도 함께 판단할 수 있다.

 - `아이디어`
    - NULL: 삭제되지 않음
    - 2026-01-20: 해당 시점에 삭제
 - `삭제 시점 활용`
    - 삭제 시점을 알 수 있음
    - 일정 기간 후 영구 삭제
    - 특정 기간 탈퇴 현황 분석
```sql
CREATE TABLE member (
    member_id BIGINT AUTO_INCREMENT PRIMARY KEY,
    username VARCHAR(50) NOT NULL,
    email VARCHAR(100) NOT NULL,
    phone VARCHAR(20),
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    deleted_at DATETIME DEFAULT NULL
);
```
<br/>

### 2-3. is_deleted vs deleted_at 비교

 - __is_deleted__
    - 저장 정보: 삭제 여부만
    - 삭제 확인: is_deleted = 0
    - 삭제 시점: 알 수 없음
    - 보관 기간 관리: 불가능
    - 기간별 분석: 불가능
    - 저장 공간: 1바이트(BOOLEAN)
    - 인덱스 효율: 좋음
 - __deleted_at__
    - 저장 정보: 삭제 여부 + 삭제 시점
    - 삭제 확인: deleted_at IS NULL
    - 삭제 시점: 알 수 있음
    - 보관 기간 관리: 가능
    - 기간별 분석: 가능
    - 저장 공간: 8바이트(DATETIME)
    - 인덱스 효율: 보통

<br/>

## 3. SOFT DELETE vs HARD DELETE

 - __HARD DELETE 장점__
    - 저장 공간 절약: SOFT DELETE는 삭제된 데이터도 계속 보관한다.
    - 쿼리 성능: SOFT DELETE를 사용하면 모든  조회 쿼리에 삭제 여부 조건이 추가된다.
    - 단순한 데이터 모델
    - 쿼리 작성의 단순함과 실수 방지: SOFT DELETE는 모든 조회 쿼리에 조건을 붙여야 한다.
 - __SOFT DELETE 장점__
    - 복구 용이: UPDATE 한 번으로 즉시 복구 가능
    - 데이터 보존: 삭제 후에도 분석, 감사에 활용 가능
    - 참조 무결성 유지: 외래 키 관계를 깨지 않고 삭제 처리

<br/>

### 3-1. 실무에서의 선택 기준

 - __SOFT DELETE를 사용하는 경우__
    - 복구 요청이 자주 발생하는 데이터
        - 회원 데이터: 탈퇴 후 복구 요청 종종 발생 (실수, 마음 변심)
    - 법적 보관 의무가 있는 데이터
        - 주문 데이터: 전자상거래법에 따라 5 년 보관 의무
        - 결제 데이터: 금융 관련 법규에 따라 보관 의무
    - 연관 데이터가 많은 핵심 엔티티
        - 상품 데이터: 주문, 리뷰, 장바구니 등 많은 테이블이 참조
    - 감사 추적이 필요한 데이터
        - 계약 데이터: 누가 언제 삭제했는지 추적 필요
```sql
-- 회원 데이터: 탈퇴 후 복구 요청이 종종 발생
CREATE TABLE member (
    member_id BIGINT AUTO_INCREMENT PRIMARY KEY,
    username VARCHAR(50) NOT NULL,
    email VARCHAR(100) NOT NULL,
    deleted_at DATETIME DEFAULT NULL  -- SOFT DELETE 적용
);

-- 주문 데이터: 전자상거래법에 따라 5년 보관 의무
CREATE TABLE orders (
    order_id BIGINT AUTO_INCREMENT PRIMARY KEY,
    member_id BIGINT NOT NULL,
    total_amount INT NOT NULL,
    order_date DATETIME DEFAULT CURRENT_TIMESTAMP,
    deleted_at DATETIME DEFAULT NULL  -- SOFT DELETE 적용
);

-- 결제 데이터: 금융 관련 법규에 따라 보관 의무
CREATE TABLE payment (
    payment_id BIGINT AUTO_INCREMENT PRIMARY KEY,
    order_id BIGINT NOT NULL,
    amount INT NOT NULL,
    payment_date DATETIME DEFAULT CURRENT_TIMESTAMP,
    deleted_at DATETIME DEFAULT NULL  -- SOFT DELETE 적용
);

-- 상품 데이터: 주문, 리뷰, 장바구니 등 많은 테이블이 참조
CREATE TABLE product (
    product_id BIGINT AUTO_INCREMENT PRIMARY KEY,
    name VARCHAR(200) NOT NULL,
    price INT NOT NULL,
    deleted_at DATETIME DEFAULT NULL  -- SOFT DELETE 적용
);

-- 계약 데이터: 누가 언제 삭제했는지 추적 필요
CREATE TABLE contract (
    contract_id BIGINT AUTO_INCREMENT PRIMARY KEY,
    client_name VARCHAR(100) NOT NULL,
    amount BIGINT NOT NULL,
    deleted_at DATETIME DEFAULT NULL,  -- SOFT DELETE 적용
    deleted_by BIGINT DEFAULT NULL     -- 삭제한 사람도 기록
);
```

 - __HARD DELETE를 사용하는 경우__
    - 로그성 데이터
        - API 호출 로그: 일정 기간 후 삭제해도 문제 없음
    - 임시 데이터
        - 장바구니: 임시 저장 데이터
    - 개인정보 완전 삭제 요청
        - 개인정보 보호법에 따르면, 사용자가 개인정보 삭제를 요청하면 완전히 삭제해야 할 수 있다.
```sql
- API 호출 로그: 일정 기간 후 삭제해도 문제없음
CREATE TABLE api_log (
    log_id BIGINT AUTO_INCREMENT PRIMARY KEY,
    endpoint VARCHAR(200) NOT NULL,
    response_time INT,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP-- deleted_at 없음: HARD DELETE 사용
);

-- 오래된 로그 삭제
DELETE FROM api_log 
WHERE created_at < DATE_SUB(NOW(), INTERVAL 30 DAY);

-- 장바구니: 임시 저장 데이터
CREATE TABLE cart_item (
    cart_item_id BIGINT AUTO_INCREMENT PRIMARY KEY,
    member_id BIGINT NOT NULL,
    product_id BIGINT NOT NULL,
    quantity INT NOT NULL,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP
    -- deleted_at 없음: HARD DELETE 사용
);
```

## 4. SOFT vs HARD vs STATUS

규모가 있는 커머스 시스템에서는 상품이나 주문 테이블에 deleted_at 컬럼을 만들지 않는 경우가 많다. 삭제라는 행위보다 더 구체적인 상태 변경이 필요하기 때문이다.

이분법적인 SOFT DELETE로는 다양한 비즈니스 요구사항을 처리하기 어렵다.

 - status 컬럼을 사용하여 생명주기 관리
```sql
-- status 컬럼을 사용한 상품 테이블 예시
CREATE TABLE product (
    product_id BIGINT AUTO_INCREMENT PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    price INT NOT NULL,
    status VARCHAR(20) NOT NULL DEFAULT 'ON_SALE', -- 판매 상태 (ON_SALE, STOP_SALE, SOLD_OUT)
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP
)
```
<br/>

### 4-1. 언제 무엇을 써야 할까?

 - __상태 기반 관리__
    - 비즈니스 프로세스가 복잡하고 데이터의 생명주기가 중요한 경우
    - 예시: 상품(판매중/품절/판매중지), 주문(결제대기/완료/취소/환불), 배송(준비/이동/완료)
    - 방법: deleted_at 없이 status 컬럼만 사용
 - __SOFT DELETE__
    - 단순히 데이터의 존재 유무가 중요하고, 복구 가능성만 열어두면 되는 경우
    - 예시: 댓글, 게시글, 좋아요, 회원(탈퇴)
    - 방법: status 컬럼 없이 deleted_at 컬럼 사용
    - 참고: 회원의 경우도 서비스가 복잡해서 다양한 상태가 있다면 상태 기반 관리를 적용하는 것이 좋다.
 - __HARD DELETE__
    - 데이터 보존 가치가 없는 경우
    - 예시: 장바구니, 로그, 임시데이터
 - __마무리__
    - 삭제는 기술이 아니라 정책이다. (복구/법/감사/분석/무결성)
    - 핵심 도메인은 보통 삭제가 아니라 상태로 관리한다.
    - SOFT DELETE는 편하지만 비용(쿼리/인덱스/휴먼에러/용량)을 치른다.

<br/>

## 5. SOFT DELETE와 이력 테이블

 - __이상적인 시나리오__
    - 이력 테이블에 모든 데이터가 남아있다. 그러면 메인 테이블에서는 HARD DELETE로 지워버리면 되지 않을까?
    - 외래키 제약 조건
    - 참조 무결성: product 테이블의 경우 orders, cart 테이블에서 product_id를 참조하고 있다. 참조되는 부모 데이터는 HARD DELETE 할 수 없다.
 - __정리__
    - SOFT DELETE와 이력 테이블은 서로 대체재가 아니라 보와냊다

## 6. SOFT DELETE와 인덱스 설계

SOFT DELETE를 도입하면 모든 조회 쿼리에 `WHERE deleted_at IS NULL` 조건이 붙게 된다. 이는 데이터베이스 성능, 특히 인덱스 설계에 큰 영향을 미친다.

 - __잘못된 인덱스 설계__
    - deleted_at을 인덱스의 첫 번쨰 컬럼으로 두는 것
    - deleted_at 인덱스의 효과가 거의 없고 비효율적이다.
    - 대부분 조회가 (비즈니스 조건) + deleted_at IS NULL 이므로 선두는 비즈니스 조건이 되는게 자연스럽다.
 - __올바른 인덱스 설계__
    - 일반적인 경우: deleted_at은 인덱스에 포함하지 않거나 마지막에 둔다.
        - 대부분 비즈니스 키의 변별력이 훨씬 높다. DB 옵티마이저는 name으로 데이터를 거른 뒤, 남은 소수의 데이터 중에서 deleted_at을 필터링하는 것이 훨씬 빠르다고 판단한다.
    - 커버링 인덱스가 필요한 경우
        - 쿼리 성능을 극대화하기 위해 인덱스만으로 쿼리를 끝내는 커버링 인덱스를 사용한다면 deleted_at을 인덱스 뒤쪽에 포함시켜야 한다.

### 6-1. UNIQUE 제약조건과 SOFT DELETE의 충돌

 - __상황1__
    - 탈퇴 ID로 가입하는 경우
```sql
-- 1. userA 가입
INSERT INTO member (login_id, deleted_at) VALUES ('userA', NULL);

-- 2. userA 탈퇴
UPDATE member SET deleted_at = NOW() WHERE login_id = 'userA';

-- 3. 새로운 userA 가입 시도
INSERT INTO member (login_id, deleted_at) VALUES ('userA', NULL);

-- Error Code: 1062. Duplicate entry 'userA' for key 'member.uq_login_id'

-- 해결 방법 1: 탈퇴 시 값을 변경하기 (추천)
UPDATE member 
SET deleted_at = NOW(),
    login_id = CONCAT(login_id, '_deleted_', UNIX_TIMESTAMP())
WHERE member_id = 3;

-- 해결 방법 2: deleted_at을 UNIQUE 인덱스에 포함하기 (비추천)
-- login_id, deleted_at으로 UNIQUE 인덱스 걸기
```
