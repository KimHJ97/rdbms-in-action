# 공통 코드 설계

## 1. 공통 코드 테이블 설계

 - 그룹 코드와 상세 코드 분리
 - 추가 속성
    - 추가 속성에 대해서 attr1, attr2, .. 로 관리할 수 있지만, 어떤 그룹은 속성 1개만 필요한데 특정 그룹 떄문에 의미 없는 컬럼이 계속 늘어나는 문제가 발생한다.
    - 속성의 개수가 가변적이고, 그룹마다 필요한 속성이 제각각일때는 EAV(Entity-Attribute-Value) 방식을 사용한다. 다만, EAV 방식은 조회 성능이 떨어질 수 있고, 데이터를 가져와서 애플리케이션에서 가공하거나 복잡한 조인 쿼리를 작성해야 한다는 단점이 있다.
```sql
-- 그룹 코드 테이블
CREATE TABLE common_code_group (
  group_code VARCHAR(50) PRIMARY KEY,
  group_name VARCHAR(100) NOT NULL,
  description VARCHAR(500),
  attr1_name VARCHAR(50),
  attr2_name VARCHAR(50),
  attr3_name VARCHAR(50),
  use_yn CHAR(1) NOT NULL DEFAULT 'Y',
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
);

-- 상세 코드 테이블
CREATE TABLE common_code_detail (
  group_code VARCHAR(50) NOT NULL,
  code VARCHAR(50) NOT NULL,
  name VARCHAR(100) NOT NULL,
  description VARCHAR(500),
  attr1 VARCHAR(100),
  attr2 VARCHAR(100),
  attr3 VARCHAR(100),
  sort_order INT NOT NULL DEFAULT 0,
  use_yn CHAR(1) NOT NULL DEFAULT 'Y',
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (group_code, code),
  FOREIGN KEY (group_code) REFERENCES common_code_group(group_code)
);
```

## 2. 공통 코드의 단점과 해결방안

 - 문제 1: SQL이 복잡해진다.
    - 코드 이름을 찾기 위해 공통 코드와 조인해야한다.
 - 문제 2: 코드 이름 조회 로직이 중복된다.
    - 모든 곳에서 공통 코드 조인을 반복해야 한다.
 - 문제 3: SELECT 결과에 항상 이름 필드가 필요하다.


### 해결방안 1: 애플리케이션에서 공통 코드 조회

 - 방식
   - SQL은 코드값만 조회한다.
   - 애플리케이션에서 공통 코드 테이블을 별도로 조회한다.
   - 애플리케이션에서 코드값을 이름으로 변환한다.
 - 장점
   - SQL이 단순해진다.
   - 공통 코드 조회 로직을 한 곳에서 관리할 수 있다.
   - 필요한 곳에서 언제든지 코드 이름을 조회할 수 있다.
 - 단점
   - 다량의 SQL 실행 문제: 공통 코드를 조회하는 쿼리가 추가로 실행된다.
```SQL
-- 1. 주문 목록 조회 (공통 코드 조인 없음)
SELECT o.order_id, m.name AS member_name, m.grade, o.order_status, o.total_amount
FROM orders o
JOIN members m ON o.member_id = m.member_id
ORDER BY o.order_id;

-- 2. 공통 코드 목록 조회(주문 상태, 회원 등급 등)
SELECT code, name FROM common_code_detail WHERE group_code = 'ORDER_STATUS';
SELECT code, name FROM common_code_detail WHERE group_code = 'MEMBER_GRADE';
```

 - 애플리케이션에서 코드값을 이름으로 변환
```java
// 3. 애플리케이션에서 코드 목록을 MAP(Key-Value) 형태로 저장해두고
// 주문 목록의 코드값을 이름으로 변환한다.
// 실무에서는 더 편리하게 재사용할 수 있도록 공통 코드를 넣으면 코드값이 나오는 클래스나 함수를 만들어서 사용하면 된다.
orderStatusMap = {ORDER: '주문접수', PAID: '결제완료', ..};
memberGradeMap = {NORMAL: '일반회원', VIP: 'VIP회원', ..};
order.orderStatusName = orderStatusMap[order.orderStatus];
order.gradedName = memberGradeMap[order.grade];

String getCodeName(String codeGroup, String code);
order.orderStatusName = code.getCodeName("ORDER_STATUS", order.orderStatus);
```

### 해결방안 2: 캐싱을 통한 애플리케이션 공통 코드 조회 단점 극복

 - __공통 코드 특성__
   - 데이터가 매우 적다: 수백 개를 넘지 않는다.
   - 변경이 거의 없다: 한 번 정의되면 거의 변경되지 않는다. 새로운 코드가 추가되거나 표시 이름이 변경될 수도 있지만 빈도가 매우 적다.
   - 조회가 매우 빈번하다: 조회는 매우 빈번하게 발생한다.
 - __메모리 캐싱의 위력__
   - L1 캐시: 1ns
   - 메모리(RAM): 100ns
   - SSD: 100,000ns
   - 네트워크(동일 데이터센터): 500,000ns
   - 네트워크(해외): 150,000,000ns
   - 메모리 접근과 네트워크 접근의 차이는 약 5,000배이다. 실제로는 네트워크 지연, 데이터베이스 처리 시간 등이 추가되어 그 차이는 훨씬 커진다.

#### 로컬 메모리 캐싱

 - 가장 단순한 캐싱 방법은 애플리케이션을 시작할 때 애플리케이션의 메모리에 공통 코드를 모두 불러서 올려두는 것이다.
```java
// 의사 코드
class CommonCodeCache {
   // 캐시 저장소: Map<그룹코드, Map<코드, 이름>>
   private Map<String, Map<String, String>> cache;

   // 애플리케이션 시작 시 캐시 로딩
   void init() {
      // DB에서 모든 공통 코드 조회
      List<CommonCode> codes = db.query(
         "SELECT group_code, code, name FROM common_code_detail WHERE use_yn = 'Y'"
      );

      // 캐시에 저장
      for (code in codes) {
         cache[code.groupCode][code.code] = code.name;
      }
   }

   // 코드 이름 조회 (메모리에서 즉시 반환)
   String getName(String groupCode, String code) {
      return cache[groupCode][code];
   }
}
```

#### 캐시 동기화 문제

 - 문제 상황: 공통 코드 테이블에 데이터 변경시 DB에 변경되었지만, 캐싱 데이터에는 변경되지 않는다.
 - 해결책: 관리자 페이지에서 캐시 갱신. 관리자가 공통 코드를 수정할 때 캐시도 함께 갱신한다.
```java
void updateCommonCode(String groupCode, String code, String newName) {
   // 1. DB 업데이트
   db.execute("UPDATE common_code_detail SET name = ? WHERE group_code = ? ANd code = ?", newName, groupCode, code);

   // 2. 캐시 갱신
   CommonCodeCache.refresh();
}
```
<br/>

 - 문제 상황: 다중 서버 환경의 문제
 - 해결책: 모든 서버에 캐시 갱신 요청
   - 모든 서버 목록을 관리해야 한다.
   - 서버 추가/제거될 때마다 목록을 업데이트해야 한다.
   - 일부 서버에 요청이 실패하면 어떻게 처리할 것인가?
   - 서버가 수백 대라면 수백 번의 HTTP 요청이 필요하다.
```java
void updateCommonCode(String groupCode, String code, String newName) {
   // 1. DB 업데이트
   db.execute("UPDATE common_code_detail SET name = ? WHERE group_code = ? ANd code = ?", newName, groupCode, code);

   // 2. 모든 서버에 캐시 갱신 요청
   for (server in getAllServers()) {
      http.post(server + "/cache/refresh");
   }
}
```
<br/>

 - Redis 같은 중앙 캐시 사용
   - 중앙에 Redis 같은 캐시 서버를 두고, 모든 애플리케이션 서버가 이 캐시를 공유하는 방식
   - 모든 서버가 Redis에서 새 값을 사용한다.
   - 단점: Redis 조회도 네트워크 호출이다.

#### TTL을 활용한 최적의 전략

 - 핵심 아이디어
   - 공통 코드를 로컬 메모리에 캐싱한다. (빠른 조회)
   - 캐시에 TTL(유효 기간)을 설정한다. (예: 1분)
   - TTL이 만료되면 데이터베이스에서 다시 로딩한다. (자동 동기화)
 - 설명
   - 1분마다 자동으로 DB에서 공통 코드를 조회한다. 그리고 메모리의 공통 코드 데이터를 DB의 최신 데이터에 맞추어 갱신한다.
```java
// 의사 코드
class CommonCodeCache {
   private Map<String, Map<String, String>> cache;
   private DateTime lastLoadTime;
   private int TTL_SECONDS = 60; // 1분

   String getName(String groupCode, String code) {
      // TTL 만료 확인
      if (isExpired()) {
         refresh(); // 캐시 갱신
      }
      return cache[groupCode][code];
   }

   boolean isExpired() {
      return (now() - lastLoadTime) > TTL_SECONDS;
   }

   void refresh() {
      // DB에서 다시 로딩
      cache = loadFromDatabase();
      lastLoadTime = now();
   }
}
```
<br/>

 - __로컬 캐시 + TTL 전략__
   - 네트워크 호출 없이 메모리에서 즉시 조회
   - TTL 만료 시 자동으로 데이터베이스와 동기화
   - 다중 서버 환경에서도 복잡한 동기화 로직 불필요
   - 구현이 상대적으로 간단
```java
@Slf4j
@Component
public class CommonCodeCache {

    private final CommonCodeRepository commonCodeRepository;

    /**
     * groupCode -> (code -> CommonCodeDetail)
     */
    private volatile Map<String, Map<String, CommonCodeDetail>> cache = Collections.emptyMap();

    private volatile LocalDateTime lastRefreshTime;

    public CommonCodeCache(CommonCodeRepository commonCodeRepository) {
        this.commonCodeRepository = commonCodeRepository;
    }

    @PostConstruct
    public void init() {
        refresh();
    }

    @Scheduled(fixedDelay = 60000)
    public void refreshScheduled() {
        refresh();
    }

    public void refresh() {
        try {
            List<CommonCodeEntity> entityList = commonCodeRepository.findAllActiveCodes();

            Map<String, Map<String, CommonCodeDetail>> newCache = new LinkedHashMap<>();

            for (CommonCodeEntity entity : entityList) {
                if (entity == null || isBlank(entity.getGroupCode()) || isBlank(entity.getCode())) {
                    continue;
                }

                CommonCodeDetail detail = CommonCodeMapper.toDetail(entity);

                newCache
                        .computeIfAbsent(detail.getGroupCode(), key -> new LinkedHashMap<>())
                        .put(detail.getCode(), detail);
            }

            Map<String, Map<String, CommonCodeDetail>> immutableCache = new LinkedHashMap<>();
            for (Map.Entry<String, Map<String, CommonCodeDetail>> entry : newCache.entrySet()) {
                immutableCache.put(
                        entry.getKey(),
                        Collections.unmodifiableMap(new LinkedHashMap<>(entry.getValue()))
                );
            }

            this.cache = Collections.unmodifiableMap(immutableCache);
            this.lastRefreshTime = LocalDateTime.now();

            log.info("CommonCodeCache refreshed. groupCount={}, totalCodeCount={}, lastRefreshTime={}",
                    this.cache.size(), entityList.size(), this.lastRefreshTime);

        } catch (Exception e) {
            log.error("Failed to refresh CommonCodeCache. keep previous cache. lastRefreshTime={}",
                    this.lastRefreshTime, e);
        }
    }

    public CommonCodeDetail getDetail(String groupCode, String code) {
        Map<String, CommonCodeDetail> groupMap = cache.get(groupCode);
        return groupMap != null ? groupMap.get(code) : null;
    }

    public String getName(String groupCode, String code) {
        CommonCodeDetail detail = getDetail(groupCode, code);
        return detail != null ? detail.getCodeName() : null;
    }

    public String getValue(String groupCode, String code) {
        CommonCodeDetail detail = getDetail(groupCode, code);
        return detail != null ? detail.getCodeValue() : null;
    }

    public String getDescription(String groupCode, String code) {
        CommonCodeDetail detail = getDetail(groupCode, code);
        return detail != null ? detail.getDescription() : null;
    }

    public List<CommonCodeDetail> getCodeList(String groupCode) {
        Map<String, CommonCodeDetail> groupMap = cache.get(groupCode);
        if (groupMap == null || groupMap.isEmpty()) {
            return Collections.emptyList();
        }
        return Collections.unmodifiableList(new ArrayList<>(groupMap.values()));
    }

    public List<String> getGroupCodeList() {
        return Collections.unmodifiableList(new ArrayList<>(cache.keySet()));
    }

    public boolean containsGroup(String groupCode) {
        return cache.containsKey(groupCode);
    }

    public boolean containsCode(String groupCode, String code) {
        Map<String, CommonCodeDetail> groupMap = cache.get(groupCode);
        return groupMap != null && groupMap.containsKey(code);
    }

    public LocalDateTime getLastRefreshTime() {
        return lastRefreshTime;
    }

    public void forceRefresh() {
        refresh();
    }

    private boolean isBlank(String value) {
        return value == null || value.trim().isEmpty();
    }
}

// 스케줄링 설정
@Configuration
@EnableScheduling
public class SchedulingConfig {
}
```

## 3. 공통 코드 vs 애플리케이션 ENUM

### 3-1. 애플리케이션에서 공통 코드를 직접 사용하는 경우

주문 상태는 단순한 표시 목적을 넘어서 애플리케이션의 비즈니스 로직에 깊이 관여한다.

 - `공통 코드만 적용한 방식의 단점`
    - 오타로 인한 버그
    - 코드 변경 시 추적 어려움
    - 자동 완성 지원 없음
    - 타입 안정성 없음
```java
// 1. 주문 취소 가능 여부 확인
boolean canCancel(Order order) {
    // 주문접수, 결제완료 상태에서만 취소 가능
    if (order.status == "ORDER" || order.status == "PAID") {
        return true;
    }
    return false;
}

// 2. 배송 시작 처리
void startShipping(Order order) {
    // 결제 완료 상태에서만 배송 시작 가능
    if (order.status != "PAID") {
        throw new Exception("결제 완료 상태에서만 배송을 시작할 수 있습니다.");
    }
    order.status = "SHIPPING";
    db.update(order);
}

// 3. 환불 처리
void processRefund(Order order) {
    // 취소된 주문만 환불 가능
    if (order.status != "CANCEL") {
        throw new Exception("취소된 주문만 환불할 수 있습니다.");
    }
    // 환불 로직..
}

// 4. 주문 상태에 따른 버튼 표시
List<String> getAvailableActions(Order order) {
    List<String> actions = new ArrayList();

    if (order.status == "ORDER") {
        actions.add("결제하기");
        actions.add("주문취소");
    } else if (order.status == "PAID") {
        actions.add("배송조회");
        actions.add("주문취소");
    } else if (order.status == "SHIPPING") {
        actions.add("배송조회");
    } else if (order.status == "DELIVERED") {
        actions.add("리뷰작성");
        actions.add("재구매");
    } else if (order.status == "CANCEL") {
        actions.add("환불조회");
    }

    return actions;
}
```

### 3-2. ENUM 정의

 - ENUM의 핵심은 문자열이 아니라 상수가 정의된다는 점이다. 정의되지 않은 잘못된 단어를 사용하면 컴파일 오류가 발생한다.
 - __ENUM 문제__
    - 표시 이름 변경시 재배포 필요
    - 추가 속성 관리의 어려움
```java
// ENUM 정의
@Getter
@AllArgsConstructor
public enum OrderStatus {
    ORDER("주문접수"),
    PAID("결제완료"),
    SHIPPING("배송중"),
    DELIVERED("배송완료"),
    CANCEL("주문취소"),
    ;

    private final String displayName;
}

// 1. 주문 취소 가능 여부 확인
boolean canCancel(Order order) {
    // 주문접수, 결제완료 상태에서만 취소 가능
    if (order.status == OrderStatus.ORDER || order.status == OrderStatus
    .PAID) {
        return true;
    }
    return false;
}

// 2. 배송 시작 처리
void startShipping(Order order) {
    // 결제 완료 상태에서만 배송 시작 가능
    if (order.status != OrderStatus.PAID) {
        throw new Exception("결제 완료 상태에서만 배송을 시작할 수 있습니다.");
    }
    order.status = "SHIPPING";
    db.update(order);
}

// 3. 환불 처리
void processRefund(Order order) {
    // 취소된 주문만 환불 가능
    if (order.status != OrderStatus.CANCEL) {
        throw new Exception("취소된 주문만 환불할 수 있습니다.");
    }
    // 환불 로직..
}

// 4. 주문 상태에 따른 버튼 표시
List<String> getAvailableActions(Order order) {
    return switch (order.status) {
        case ORDER -> Arrays.asList("결제하기", "주문취소");
        case PAID -> Arrays.asList("배송조회", "주문취소");
        case SHIPPING -> Arrays.asList("배송조회");
        case DELIVERED -> Arrays.asList("리뷰작성", "재구매");
        case CANCEL -> Arrays.asList("환불조회");
        default -> Collections.emptyList();
    };
}
```

 - `ENUM과 데이터베이스 연동`
```java
// 저장시: ENUM -> 문자열
String statusCode = order.status.name();
db.execute("INSERT INTO orders (status) VALUES (?)", statusCode);

// 조회시: 문자열 -> ENUM
String statusCode = rs.getString("status");
OrderStatus status = OrderStatus.valueOf(statusCode);
```


#### 공통 코드 vs 애플리케이션 ENUM 선택 방법

 - __공통 코드 테이블(DB)__
    - 용도: 단순 목록 조회, 화면 표시
    - 코드 안정성: 낮음 (문자열 사용, 오타 위험)
    - 변경 유연성: 높음 (DB만 수정하면 반영)
    - 자동 완성: 지원 안함
    - 관리 주체: DBA, 개발자, 운영자
 - __애플리케이션 ENUM__
    - 용도: 비즈니스 로직 분기 처리
    - 코드 안정성: 높음 (컴파일 체크, 타입 안전)
    - 변경 유연성: 낮음 (코드 수정 및 재배포 필요)
    - 자동 완성: IDE 강력 지원
    - 관리 주체: 개발자
 - __명확한 기준__
    - 애플리케이션 로직에 사용되는가? -> ENUM 사용
        - if 와 같이 코드 내에서 분기 처리가 필요하거나 비즈니스 로직의 기준이 되는 데이터라면 반드시 ENUM을 사용
        - 이유: 오타 방지, 자동 완성, 리팩토링 용이성 등 코드의 품질과 유지보수성을 위해 필수적
        - 예시: 주문 상태(접수/결제/배송), 회원 등급(일반/VIP), 결제 수단(카드/현금) 등
    - 단순한 목록으로만 보여주는가? -> 공통 코드 테이블 사용
        - 로직에는 전혀 관여하지 않고, 단순히 사용자에게 선택지를 제공하거나 화면에 텍스트를 보여주기 위한 용도라면 공통 테이블 사용
        - 이유: 비즈니스 로직보다는 운영 설정에 가까움. 항목이 추가되거나 이름이 변경되어도 코드를 다시 배포하지 않고 DB만 수정해서 즉시 반영할 수 있어야 함
        - 예시: 지역 코드(서울/경기/부산), 은행 코드(국민/신한/우리), 취미 목록, 가입 경로 등
    - 변경이 매우 빈번한가? -> 공통 코드 테이블 사용
        - 로직에 일부 사용되더라도 하루에도 몇 번씩 바뀔 수 있는 데이터라면 ENUM으로 관리하기 어려움. 코드이 안정성을 일부 포기하더라도 운영의 유연성을 위해 공통 코드 테이블 사용

### 3-3. 하이브리드 전략

 - __핵심 아이디어__
    - ENUM: 코드값 정의, 타입 안전성, 비즈니스 로직
    - 공통 코드: 표시 이름, 추가 속성, 운영 유연성
 - __하이브리드 전략 운영 규칙__
    - 코드 추가는 개발자가 담당
    - 속성 변경은 운영자가 담당
    - ENUM과 공통 코드 동기화
        - 이를 보장하기 위해 검증용 테스트 케이스를 작성하는게 안전

<br/>

#### 하이브리드 전략 예시

 - __STEP 1: ENUM 정의__
    - 표시 이름과 속성은 ENUM에 정의하지 않는다.
```java
public enum OrderStatus {
    ORDER,
    PAIDE,
    SHIPPING,
    DELIVERED,
    CANCEL;
}
```

 - __STEP 2: 공통 코드 테이블__
```sql
INSERT INTO common_code_detail (
    group_code, code, name, name_en, sort_order
) VALUES 
('ORDER_STATUS', 'ORDER', '주문접수', 'Order Received', 1),
('ORDER_STATUS', 'PAID', '결제완료', 'Payment Complete', 2),
('ORDER_STATUS', 'SHIPPING', '배송중', 'Shipping', 3),
('ORDER_STATUS', 'DELIVERED', '배송완료', 'Delivered', 4),
('ORDER_STATUS', 'CANCEL', '주문취소', 'Cancelled', 5);
```

 - __STEP 3: 비즈니스 로직에서는 ENUM 사용__
```java
boolean canCancel(Order order) {
    return order.status == OrderStatus.ORDER ||
           order.status == OrderStatus.PAID;
}

void startShiiping(Order order) {
    if (order.status != OrderStatus.PAID) {
        throw new Exception("결제완료 상태에서만 배송을 시작할 수 있습니다.");
    }
    order.status = OrderStatus.SHIPPING;
}
```

 - __STEP 4: 표시 이름은 DB나 캐시의 공통 코드에서 조회__
```java
String getstatusDisplayName(OrderStatus status) {
    return CommonCodeCache.getName("ORDER_STATUS", status.name());
}
```

 - __동기화 검증__
    - 테스트를 CI/CD 파이프라인에 포함시키면, 배포전에 동기화 문제를 발견할 수 있다.
```java
@Test
void ENUM과_공통코드_동기화_검증() {
    // 1. ENUM에서 모든 코드값 조회
    Set<String> enumCodes = Arrays.stream(OrderStatus.value())
        .map(e -> e.name())
        .collect(toSet());
    
    // 2. 공통 코드 테이블에서 모든 코드값 조회
    Set<String> dbCodes = db.query(
        "SELECT code FROM common_code_detail WHERE group_code = 'ORDER_STATUS'"
    ).stream().map(r -> r.code).collect(toSet());

    // 3. 두 집합이 일치하는지 검증
    assertEquals(enumCodes, dbCodes, "ENUM과 공통 코드 테이블의 코드가 일치해야 합니다.")
}
```

## 4. 공통 코드 설계와 비즈니스 설계의 차이

 - __공통 코드에 대리키를 사용하지 않는 이유__
    - member, orders 테이블을 설계할 때 BIGINT형 AUTO_INCREMENT를 기본키로 사용한다. 시스템 내부에서 관리하는 의미 없는 숫자를 키로 사용하는 것이 비즈니스 키 변경 등 여러 변수에 대처하기 좋기 때문이다.
    - 공통 코드 테이블은 code라는 문자열을 복잡 키로 구성해서 기본키로 사용한다.
        - 데이터 가독성: 값을 보고 직관적으로 어떤 값인지 알 수 있음
        - 애플리케이션 매핑의 용이성
 - __공통 코드 외래 키를 사용하지 않는 이유__
    - `복합 키 구조의 문제`
        - common_code_detail 테이블의 기본 키는 group_code와 code를 합친 복합 키다.
        - 관계형 데이터베이스에서 외래 키를 걸려면 참조하는 테이블의 기본 키 구성을 그대로 따라야 한다.
            - order 테이블의 주문 상태 코드에 외래 키를 걸려면 group_code 컬럼도 필요하게 된다.
    - `성능과 유연성`
        - 주문 테이블처럼 데이터가 대량으로 쌓이는 트랜잭션 테이블에 외래 키를 걸면, 데이터를 입력할 때마다 공통 코드 테이블을 조회해서 값이 맞는지 확인하는 과정이 발생한다. 이는 미세하지만 성능 저하의 원인이 된다.
        - 공통 코드는 애플리케이션 레벨(ENUM 등)에서 이미 검증된 데이터만 들어오도록 통제하는 것이 일반적이다. DB 레벨에서 외래 키로  한 번더 강제하지 않아도 데이터 정합성이 크게 훼손되지 않는다.
